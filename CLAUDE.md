# awesome-vtt-sotdl-builder – project notes and specification

Guided character builder for **Shadow of the Demon Lord** (`demonlord` system 6.1.x, built against 6.1.11) on Foundry VTT **v14**, by Stefano Pignataro. Part of the Awesome VTT series by name only (see "Independence").

## Origin and scope (user's request, 2026-10-10)
- The user asked for "a new, separate module to the awesome-vtt series that uses hero-mancer as a source but allows to create characters in Shadow of the Demon Lord".
- **Hero Mancer as a source = design source, not a dependency.** Hero Mancer (`../hero-mancer`, MIT, by Tyler/Sayshal) is a minified, dnd5e-only bundle that requires `3ds-atlas`, so it can't be reused at runtime. This module re-implements its UX for SotDL: one window, sidebar with a live preview (portrait, scores, characteristics) and the steps with badges for choices left, Back / Next / Create footer with a progress bar, draft auto-saved on the user, a launch button in the Actors directory header. No Hero Mancer code was copied.
- Out of scope for now (possible later): GM approval queue, compare/pin, random full build, Create-Actor dialog option, other languages than English.

## Independence (user asked, 2026-10-10)
- **Completely detached from `awesome-vtt-core`** and from the table / phone / shared-inventory modules: no imports, no `requires`, no hooks into them, and they don't reference it. Its only relationships: the `demonlord` system, and `sdlc-1000` as a recommendation.
- The series' "keep table and phone in sync through core" rule doesn't apply here. If the table or phone module should ever offer a "Build character" button, use this module's `api.open()` and ask the user first (that would touch the sync rule).

## Content: nothing bundled
- The demonlord system ships only weapons, armor, ammunition, languages (and macros, tables, a guide). Ancestries, paths, talents, spells and professions are Schwalb Entertainment's content and come from compendium modules the group owns (here `sdlc-1000`, "SDLC – Core", with 6 ancestries, 4 novice / 16 expert / 64 master paths, 102 professions, 542 spells, 610 talents, tables) or from world items.
- `content.mjs` indexes every visible Item compendium (except packs whose id contains "creature") plus visible world items, with `type`, `system.type` (path tier), `system.tradition`, `system.rank`. Nothing about the book is hard-coded except: the default of the `equipmentPage` setting (the core book's "Starting Equipment" page uuid), and the table names `Profession Types`, `<Kind> Professions`, `Wealth`, `Interesting Things Tables` (looked up by name in world tables and visible RollTable packs; features hide when missing).

## Rules implemented (from the core book text in `sdlc-1000.journals`, checked 2026-10-10)
- Starting level: book assumes 0; to start higher it suggests 1, 3 or 7 ("Character Creation"). Setting `startLevel` (0–10); GMs can change it in the window, players only with `playersChooseLevel`.
- Advancement table: novice path at 1 (benefits at 1, 2, 5, 8), expert at 3 (3, 6, 9), master at 7 (7, 10), ancestry benefits at 4. `TIERS` in constants.
- Attributes: starting scores from the ancestry; **once, +1 to one score and −1 to another** ("Adjusting Scores"). Modifier = score − 10.
- **Ancestry bonus (not in the compendium's text):** an ancestry whose level 0 has a "choose" `attributeSelect` (in the core data only Human, stored as `choosethree`) gets "+1 to one attribute". This is the user-facing recollection of the Human rule, unverified against the book (the Human trait block isn't in the compendium). Fixed ancestries get only the general adjustment. Revisit if the user reports otherwise.
- Path levels: `choosetwo` = +value (1) to two attributes (novice 1, expert 3), `choosethree` = three (master 7), `fixed` = all, `""` = none. A level's `talentspick` = choose one (rogue 2/8, fighter 3/6, …). Text fields `languagesText`, `magicText`, `equipmentText`, `optionsText` are shown as guidance.
- Ancestry level 4: "You either learn one spell or gain <talent>" (from the items' legacy `level4.option1text`); radio talent / spell, spell rank ≤ Power.
- Characteristics preview mirrors the system's derivation: Health = Strength + bonuses, Healing rate = ⌊Health/4⌋ + bonuses, Perception = Intellect + bonuses (max 25), Defense = Agility + bonuses (armor not counted), Power = sum, Speed = ancestry level-0 speed + later bonuses, Size = ancestry (Human chooses 1/2 or 1), Insanity limit = Will.
- **Magic limits (user's request, 2026-10-10: same guard rails as professions; standing rule: everything addable follows the real limits):** `rules.mjs` `parseMagic` reads each gained level's `magicText` per sentence into grants `{ kind: tradition|spell|choice, only }`: "make N choices" → N choices; "discover <…> tradition … or (you) learn …" → a choice, restricted to the capitalized tradition names in the phrase ("the Theurgy tradition", Druid's "the Life, Nature, or Primal tradition"); "discover one tradition" → a tradition; "learn one / two spells" → spells; a "For each choice, …" sentence is skipped (it explains the choices before it); "learn the <name> spell" is skipped because that spell is in the level's own `spells` list, which is now always given with the level (`applyLevelChoices` selects every `level.spells` entry: Spellbinder 3's Spellbound Weapon, Magician 1's Sense Magic). "Associated with your religion" isn't restricted (no religion→tradition data). All 47 distinct texts of the core data checked (2026-10-10). `magicAllowance` matches the plan's discovered traditions (`plan.traditions = [{ name, spell }]`, `spell` = the free rank 0 spell the book gives with a discovery, required) and learned spells (`plan.spells`) to the grants (bipartite matching), and checks the book's other rules: spells only from discovered traditions (the character's own in a level up, from its spells' traditions) and rank ≤ Power; the ancestry level-4 spell too (`learnable`, also the filter of the spell list; the Paths step says to discover a tradition first when there is none). UI: "Traditions (X of N)", "Spells (X of N)" (N = what can still be matched), the Discover select lists only traditions that fit a grant, add buttons disabled when a spell doesn't fit, actions refuse with a warning, removing a tradition removes its spells; over-limit or invalid choices (incl. a free spell that isn't a rank 0 spell of its tradition) and open grants count on the Magic step's badge (`remaining(plan, docs, allowance, magic)`, both allowances required). `create.mjs` `checkAllowances` re-checks professions and magic (`over`, plus a free spell per tradition) when creating and levelling up; spells added = free spells + learned + level-4 spell (`allSpells`). The Magic step shows when the gained levels grant magic or some was chosen.
- **Profession / language limit (user's request, 2026-10-10: "do not allow more professions than allowed by their level"):** `rules.mjs` `professionAllowance(plan, docs)`. The book: you begin with two professions and can trade a profession to speak another language; ancestry and path levels ≤ the character's level add more. The compendium states those grants only in `languagesText`, so `parseGrants` reads them per sentence: profession words (`profession`, `area of knowledge`, `scholarship`) + language words ("speak/add another/one additional/one/a language") → "either" (or "both" when the sentence says "and add"); profession only → profession (Warrior 1, Magician 1, Ranger 3, Priest 1's 2nd sentence); language only → language (Priest 1's 1st). All 30 texts of the core data classified correctly (checked 2026-10-10). Limits: professions ≤ 2 + profession + either grants; professions + extra languages (not the ancestry's, not `auto`) ≤ that + language grants + background results saying "speak one additional language". Add / roll / custom-profession / add-language buttons are disabled and their actions refuse at the limit; choices above it (after lowering the level or changing ancestry / path) count as missing on the step until removed; `buildCharacter` throws `AVTTSB.Create.Error.TooMany` (so the GM's side enforces it too). Required minimum: professions + extra languages ≥ 2. Applies to GMs too. Reading/writing marks are not counted.
- Professions: roll = Profession Types (d6, bold kind) → `<Kind> Professions` (d20) → matched to a profession item by name, else a new profession item with that name and the rolled text; custom names allowed. Languages: from the ancestry's level-0 `{@language Name|system}` references, plus extras; read/write per language.
- Background: the ancestry description's linked RollTables (Age, Build, Appearance, Background, Personality, Religion, …), each **picked from a dropdown, rolled, or typed** (user's request 2026-10-10: entries must be selectable). `content.mjs` `tableEntries(table)` lists results sorted by range ("4–7: text"), cached per table; RollTable results one level deep become `<optgroup>`s (Interesting Things: 6 groups, 120 entries). Inline rolls `[[/r 1d6]]` show as `1d6` (`readableText`), also in rolled text. Picking writes the entry text into the trait (change handler `data-trait-pick`, `@interesting` for the interesting thing) and re-renders; the dropdown shows the entry matching the current text, else its placeholder (typed or edited text); "Religion" also fills `system.religion.value`, "Age" fills `system.appearance.age`; interesting thing (nested table). Effects of results (Insanity, Corruption, coins) are **not** applied automatically; the Review step says so.
- Equipment: Wealth table (3d6) → lifestyle; the lifestyle's kit is read from the `equipmentPage` journal page **only on request** (the core book is one ~20 MB JournalEntry; loading a page loads all of it; cached per session). Kit paragraphs `<p><b>Lifestyle</b>: …</p>`; items from `@UUID[...]` links and `{@weapon|armor|ammunition|item name|system}` markup (not enriched by the system; matched by name, creature packs excluded); "or" choices are left to the player (chips). Purse `[[/r XdY]] coin` roll. Higher levels: 2d6 ss per level button. Free search of all weapon/armor/ammo/item entries.
- Required to create: name, ancestry, size when there's a choice, ancestry bonus when offered, complete adjustment pair, every applicable path with its attribute and pick choices, the level-4 choice (when level ≥ 4), two professions (or traded languages) and none over the allowance, every magic grant used with a rank 0 spell per discovered tradition and nothing over it. Equipment never blocks (bought gear has no rules limit).

## How a character is created (`create.mjs`)
- The plan holds only uuids and choices (`rules.mjs` `newPlan`). Whoever creates loads the documents and writes the choices **into the embedded copies**, the way the system's own item sheets store them:
  - ancestry level 0 attribute values (the system adds `value − 10` per attribute at level 0, so bonus/adjustment go there), level-0 `characteristics.size` (string), level 4 `talentspick[0].selected` when "talent";
  - path levels ≤ level: `attributes.<a>.selected`, `talentspick[i].selected` (pick matched by `uuid ?? id ?? _id`).
- Actor created first with `system.level`, owner = the requesting user, linked token, `flags.awesome-vtt-sotdl-builder.plan`; then **all items in one `createEmbeddedDocuments`** so the system's `_onCreateDescendantDocuments` → `handleCreateAncestry` / `handleCreatePath` adds the level talents (fixed + selected picks) and `embedActiveEffects` builds the level effects (disabled above the actor's level). That handler runs only on the creating user's client.
- Spells, professions, languages, equipment are embedded as plain items (spells not nested in paths). Quantity → `system.quantity` when the type has it, else repeated items.
- `assignCharacter` setting: sets `user.character` when the player has none.

## Level up (user's request, 2026-10-10: "the builder allows for level ups in addition to character generation")
- Same window opened with an actor (`api.openLevelUp(actor)`; "Level Up" in the character sheet's header menu via `getHeaderControlsActorSheetV2`, and in the Actors directory's context menu via `getActorContextOptions`), for owners of demonlord characters below level 10. Window id `awesome-vtt-sotdl-builder-levelup-<actorId>`; no draft.
- A level-up plan is `newPlan(level, fromLevel)` (no separate mode flag): only levels above `fromLevel` count — `rules.mjs` `isNewLevel` / `newLevels` drive `appliedLevels`, `levelGains`, `remaining`, `guidance`, `professionAllowance` (no base 2 and no minimum; only the new levels' grants), `gainsL4` (ancestry level 4 crossed), `pruneChoices` and `chosenTalents`. `isNewCharacter(plan)` (= ancestry level 0 is gained, `fromLevel` −1) gates every level-0 benefit: ancestry/size/bonus/adjustment/name checks, ancestry guidance and talents, the two starting professions. The ancestry and existing paths are the actor's embedded items (their uuids in the plan; `rules.mjs` `ownedBuild(actor)`, shared by the builder and `levelUpCharacter`, as are `ownedNames(actor, type)` and `knownTraditions(actor)`). Steps: Paths (new levels of owned paths, a new path at 1/3/7), Magic, Professions & Languages, Review (`createOnly` steps hidden). New level: +1 by default; GMs (or players with `playersChooseLevel`) can pick any higher level. Preview: `levelUpStats` = the actor's derived values + gains (Health follows Strength, Perception Intellect, Defense Agility; armor that fixes Defense not considered).
- Applying (`create.mjs` `levelUpCharacter`), in the order of the system's own sheet (`onSubmit` → `handleLevelChange` → update), whose helpers aren't exported: write the new levels' choices into the owned ancestry/path items (`updateEmbeddedDocuments`, only items with new levels; old levels untouched), add those levels' nested items as `createActorNestedItems` does (talents, languages, selected picks and spells; `flags.demonlord` `nestedItemId` / `parentItemId` / `levelRequired`), update `system.level`, then embed new paths (the system's `handleCreatePath` adds their levels up to the new level) plus spells, professions and extra languages not already on the actor. Smoke-tested with a mocked actor: dwarf warrior 2→3 (new Fighter path after the level update) and 3→4 (ancestry level-4 talent nested with its parent and level). Not run live.

## Players without "Create new actors"
- `createCharacter` emits `{ type: "create", requestId, plan }` on `module.awesome-vtt-sotdl-builder`; the **active GM** (`game.users.activeGM.isSelf`) handles it with the sender id from the server, checks `playersMayCreate`, and replies `{ type: "created", requestId, userId, actorId | error }` (120 s timeout on the player).
- Security: the plan is untrusted. `sanitizePlan` keeps known fields only, bounded strings/lists/numbers (`LIMITS`), uuids matching `^[A-Za-z0-9_.-]{1,200}$`, attributes from `ATTRS`, lifestyles from `LIFESTYLES`. `loadItem` accepts only top-level Items of `ALLOWED_TYPES` (and the expected type) that the **requesting user** can see (pack `testUserPermission(user, "OBSERVER")`, world item `LIMITED`). HTML in the biography is escaped. The player gets ownership of only the new actor.

## Files
- `scripts/main.mjs` settings, partials, `api` (`open`, `openLevelUp`, `CharacterBuilder`), Actors directory button (`renderActorDirectory`, `.header-actions`), Level Up launchers, socket at ready, index cache cleared on world item changes.
- `scripts/constants.mjs` ids, steps (`createOnly`, `when(plan, stats)`), tiers, `APPEARANCE`, `TRAIT_FIELDS`, limits, `LEVELS`. `scripts/content.mjs` index (per type, `equipment`, `byUuid`, precomputed `search`; packs indexed in parallel), documents, the book's markup (one `MARKUP_RE`), tables (lookups and entries cached), kits (items resolved once from the index). `scripts/rules.mjs` pure rules, incl. shared `levelKey`, `pickId`, `allSpells`, `allLanguages`, `chosenTalents`, `l4Missing`. `scripts/create.mjs` sanitize (exports `cleanText` / `cleanCount` for the form), build, create, level up, socket. `scripts/builder.mjs` the ApplicationV2 window.
- Templates: `sidebar.hbs`, `body.hbs` (dynamic partial `avtsb-step-<id>`), `footer.hbs`, `steps/*.hbs`, partial `guidance.hbs` (`avtsb-guidance`). Each part renders one root element. Only Foundry's built-in helpers (`selectOptions` for every dropdown, incl. option groups for table entries; `checked`, `localize`); search keys are precomputed (`search`), no custom helpers.
- CSS prefix `avtsb-`, language prefix `AVTTSB.`; data attributes `data-avtsb-*`.

## Window behaviour
- Simplified 2026-10-10 (user's "review and simplify"): documents synced once per render in `_prepareContext` (parallel), followed by `pruneChoices`; stats / allowance / remaining computed once per render; plan-changing actions are wrapped by `#edit` (save draft + re-render unless the handler returns `false`); `#once` runs rolls/creation one at a time and reports errors; one `removeAt` action with a `data-list` whitelist (`LISTS`). Second pass (same day, after level up and magic limits): the allowances and `remaining` from the last render are kept on the window (`this.allowance`, `this.magic`, `this.missing`) and used by the actions' limit checks and submit; `magicAllowance` caches its "one more fits?" matchings per kind+tradition and computes "X of N" room with one matching per kind; `CHARACTERISTICS` constant; `stripMarkup` (content.mjs, sync, on `MARKUP_RE`) for parsing; `pathItem` shared by create and level up; level up's nested items load in parallel.
- Change events: inputs named after plan paths (`FIELDS`: kind, length limit, what to re-render — `name` only re-renders sidebar and footer), `level`, `data-language`/`data-flag`, `data-item-qty`, `data-trait` (background tables; `TRAIT_FIELDS` maps Religion / Age onto character fields by exact label), filter controls (`data-filter-tradition`, `data-filter-ranks`). Dropdown pickers carry `data-picker`: their placeholder is ignored and they always re-render (the interesting-thing picker writes `bio.interesting` like its textarea). Search fields filter rows in the DOM (`data-filter` / `data-filter-list` / `data-search`) without re-rendering, and their text is restored after renders. Body part keeps its scroll (`scrollable: [""]`).
- Draft: `user.flags.awesome-vtt-sotdl-builder.draft = { plan, step }`, debounced 800 ms, cleared on create or Start Over.
- Magic step shown only with Power > 0, a level-4 spell, or spells already chosen; Paths only from level 1.
- Limited choices show "X of N" (user, 2026-10-10): professions, extra languages (N = what the shared allowance leaves after professions), path attribute choices and talent picks. Equipment has no limit, so it keeps a plain count. Disabled buttons are dimmed (`.avtsb-builder button:disabled`). Warnings have a bottom margin (user, 2026-10-10).

## Displayed text (fix 2026-10-10, user saw raw `@UUID[...]` in the starting kit)
- Every book text shown in the window goes through `content.mjs` `displayText`: `@UUID[uuid]{label}` → label; unlabeled `@UUID[uuid]` (the kits' items, 24 table results linking talents / creatures / a journal page, one path text) → the linked document's **name from the pack index** (`linkName`, cached; `parseUuid`; only packs the user can see; world documents from their collection), never loading the document; embedded links (journal pages, whose parent is the ~20 MB book) aren't resolved and show `AVTTSB.LinkedEntry` "(linked entry)", as does anything unknown. Then `readableText` (`{@type name|…}` → label/name, `[[/r 1d6]]` → `1d6`) and plain text. Used for kits, table entries (dropdowns), rolled results, ancestry languages, path level notes and talent-pick descriptions, magic and language guidance. Checked against the real data: all three kits and all 24 linked table results free of markup.

## Hot reload (user asked, 2026-10-10)
- The server has `hotReload: true` (Config/options.json). `module.json` opts in with `flags.hotReload` = extensions css / hbs / json, paths styles / templates / lang. Foundry v14 (client `Game#handleHotReload`) swaps CSS links, recompiles changed templates (every id in `Handlebars.templateIds[path]`, so both the window parts and the `avtsb-step-*` partials) and merges the current language's JSON, then re-renders all open windows; the builder keeps its plan, so an open build survives.
- **JavaScript is never hot-reloaded** (the client has no handler for js/mjs): after script changes, reload the page (F5). The watcher starts when the world launches, so a newly added flag needs a world relaunch.

## Upstream watch

`.github/workflows/compat-review.yml` runs daily and has Claude review this module once for each new version of a dependency, following `.github/prompts/foundry-compat.md`.
- **Game systems:** a release of a system in `relationships.systems` newer than its `verified` version.
- **Foundry core:** a new Stable build, with a light review within the verified generation and a full review for a new generation.
- **Results:**
  - The module is fine: a pull request that bumps `verified`. It goes out with the next manual release.
  - A fix: a pull request.
  - Anything that needs the owner: an issue labelled `upstream-watch` and assigned to the owner.
  - New features worth using: an `enhancement` issue.
- **Access:** Claude works with read-only access (secret `CLAUDE_CODE_OAUTH_TOKEN`). A separate job opens the pull request and issues.
- **Bookkeeping:** `.github/scripts/watch.sh` records what was reviewed on the `watch-state` branch. Run the workflow by hand with `force` to review again.
